# badge-accel — the firmware in the demo video

**This is what runs on the badge.** If you watched the video, this is the code
behind it: the logo, the live sweep chart with labelled axes, the severity-
coloured impact LEDs, and the CSV stream over USB.

It is a plain Arduino sketch, built with `arduino-cli`, and it is deliberately
separate from `firmware/` in this repo. The two exist for different reasons and
conflating them would misrepresent both:

| | `badge-accel/` (this directory) | `firmware/` |
|---|---|---|
| What it is | The demo. One sketch, one file, on the badge now | A PlatformIO HAL with a four-stage detector |
| Detection | `mg >= 1600` plus a 250 ms debounce | Amplitude → isolation → ringdown → refractory |
| Sensor config | `CTRL_REG1=0x57`, `CTRL_REG4=0x80` (100 Hz, ±2 g) | `0x77`, `0xA8` (400 Hz, ±8 g, HR) |
| Resolution | 4 mg effective (see the caveat below) | 4 mg, and the code says so |
| Tests | Verified on hardware, by hand | 19 host tests in CI |
| Validated against | The bench | 4,505 SisFall recordings |

**Which one is "right" depends on what you are asking.** This sketch works, is
tuned by hand on the real badge, and is what the video shows. `firmware/` is
the rigorous version — it corrects a register contradiction in the official HAL
guide, separates the algorithm from the hardware so CI can test it, and has
been replayed against 14.5 hours of public accelerometer data. Neither
supersedes the other yet; merging them is the obvious next step and did not fit
in an eight-hour event.

## The register caveat, stated plainly

This sketch follows the badge's HAL guide: `CTRL_REG4 = 0x80`. Bit 3 of that
register is **HR** (high resolution), and `0x80` leaves it clear, which is
10-bit mode — so the values move in steps of 4 while the comment claims
1 mg/count. The guide says "12-bit, 1 count = 1 mg" and those two statements
cannot both be true. Confirmed against the Silan SC7A20 datasheet Rev 1.3,
which publishes no sensitivity figure at all for non-HR mode.

It is left as-is here **on purpose**: this firmware was tuned and demonstrated
with these values, and silently changing the sensor configuration after the
fact would invalidate the thresholds the demo actually used. `firmware/` is
where the fix lives. See `docs/SC7A20-REGISTERS.md`.

## Layout

```
badge_accel/badge_accel.ino   the sketch — sensor, chart, LEDs, CSV stream
badge_accel/logo.h            RGB565 logo bitmap, generated by tools/make_logo.py
tools/flash_and_verify.py     build-independent flash + verify-flash + read-mac
tools/open_window.py          live plot window on the host
tools/bump_window.py          windowed bump capture
tools/bump_ndjson.py          one NDJSON object per bump, for piping onward
tools/tune*.py                threshold tuning over serial, against the live badge
tools/verify_defaults.py      confirm the on-device config after a flash
tools/make_logo.py            PNG -> logo.h
```

## Build and flash

```bash
arduino-cli compile \
  --fqbn esp32:esp32:esp32c3:CDCOnBoot=cdc,FlashSize=4M,FlashMode=dio,FlashFreq=80 \
  --output-dir badge_accel/build/esp32.esp32.esp32c3 badge_accel

python tools/flash_and_verify.py        # writes 0x0, verifies, reads MAC
```

`USB CDC On Boot: ENABLED` is not optional. Without it `Serial` goes to UART0,
whose pins go nowhere on this board, and the badge looks dead.

## On screen

- **Y axis** — `3000 / 1600 / 1000 / 0` mg in the left gutter, ticked, with the
  two reference lines named (`bump`, `1g rest`) rather than left as bare numbers.
- **X axis** — ticks every second with a `sweep 2.9s @ 98Hz` caption. The labels
  read as *time since the cursor last wrapped*, because the trace is a wrapping
  sweep rather than a scrolling window; labelling them "−1s, −2s" would be wrong
  across most of the screen.
- **Readouts** — `now` (live magnitude), `peak` (running maximum, so the hardest
  hit stays visible), and on a trip `BUMP <mg>` with the magnitude that caused it.
- **LEDs** — all six flash for 120 ms, amber at the threshold grading to red for
  a hard strike, scaled over the same 1600→3000 mg range as the chart so the
  lights and the trace agree about what "hard" means.

Brightness is capped at **48/255**. The HAL guide warns that six LEDs at full
white can brown out this board on AA power, and a brown-out at the instant of an
impact is indistinguishable from a crash in the one moment the I²C read matters.
Raise it only on USB, and only knowing that.

## Not in this directory

The stock Hack the North event firmware backup (`event-firmware-backup.bin`,
4 MB) is kept locally and **not committed**. It is their image, not ours to
redistribute — but take your own backup before re-flashing a badge, because
replacements are limited and re-flashing is flagged experimental by the people
who built it.
